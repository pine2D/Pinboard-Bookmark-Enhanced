# Privacy Policy: Bookmark Enhanced

**Last updated:** 2026-11-02

## Summary

Bookmark Enhanced is local-first and bring-your-own-key. It has no developer servers, no analytics, no tracking, and no telemetry; the developer never receives your data. The extension uses your selected Pinboard, Karakeep or linkding service for bookmark features and contacts other services only as described below. Bookmark-status checks and offline-save retries can run automatically; features you turn on, such as Wayback archiving, key-points skim, the unread badge, Google Drive sync, and video subtitles you have already granted, can also make automatic requests. After you have granted access to the online dictionary, opening a saved word on the Library page can also look it up automatically.

Google Drive sync remains off until you explicitly connect it on a device. Once connected, it syncs the personal library’s vocabulary, highlights, notes, complete AI dictionary entries with their supplements, and saved Ask conversations through the extension's private Google Drive application-data folder; disconnecting that device stops it. Drive does not sync settings, credentials, unowned legacy highlights, or dictionary packs.

Bookmarking and the configured features described under **Network requests** can transmit the specific data needed for those features. You can optionally enable **settings sync** (off by default); ordinary settings (not saved bookmarks or page content) are then synced across your devices through Chrome's built-in account sync.

Settings sync is implemented with Chrome's `chrome.storage.sync`. Whether ordinary settings sync is enabled remains a per-device choice. The separate credential-sync preference (**Sync credentials for this Google account**) is an account-wide marker, but credentials are read from or written to Chrome Sync only on devices where ordinary settings sync is also enabled. New users start with credential sync off. During upgrade, if the account-wide marker is missing but Chrome Sync already contains a non-empty credential/export-target token, or the old device-local credential-sync preference was on, the marker is initialized on to preserve that existing opt-in and avoid credential loss; otherwise it is initialized off. API keys, tokens, passwords, configured Webhook URLs, and other export-target credentials stay local unless both settings sync and this account-wide credential option are enabled. These values are obfuscated at rest (not cryptographically encrypted). Public service requests use HTTPS; configured AI and Webhook endpoints may use plain HTTP only for the literal loopback hosts listed under **Network requests**. The extension has no developer server; automatic requests are limited to the core and enabled behaviors documented below.

While credential sync is enabled, each participating device also retains its last observed cloud credential snapshot locally. If another device turns credential sync off and removes the cloud copy, that local snapshot remains available. A device that was offline during a credential change can retain only the older snapshot it last received.

New offline-queue records never store API tokens. They store the bookmark fields listed above plus a non-secret bookmark connection binding: the Pinboard username, or the selected self-hosted service, server and verified user/connection identity. Legacy Pinboard records are rewritten without their stored token field. Retry requires the current credential for the same connection; logout or a connection switch leaves the item queued. When an access-gateway failure pauses automatic retries, only a non-secret local pause record is stored: the connection identity and the failure reason.

Bookmark-derived records and caches carry a non-secret connection owner. This applies to the offline queue, tag caches, recent-tag state, Batch progress, tag-cleanup state and bookmark metadata in reader handoffs. Reading data uses the separate personal library identity: vocabulary, highlights, notes, Ask history, translations and dictionary archives remain available when you change bookmark services. Both kinds of owner binding exclude API tokens; the bindings themselves create no network requests. Dictionary lookup reuse still depends on the word and language pair, not the current AI provider or model.

Vocabulary TSV exports are local files created only when you choose an export action. The complete format includes a locally derived WordID, language, base form, notes, all context/source associations, dictionary provenance, groups, learning status and timestamps, plus any local supplemental definition. It excludes credentials and Drive protocol state. The original six-field TSV remains available; JSON backup is the format for restoring data into this extension.

Manual backups are plaintext schema v3 JSON files you explicitly export. They contain settings and themes. You can separately include reader highlights and notes, which contain page URLs, page titles, selected text, note text, highlight colors, and timestamps. You can also include the personal library’s vocabulary records, including the vocabulary fields listed in the table above. OAuth data, Drive account data, version vectors, outbox, tombstones, pending batches, dictionary packs, and the AI dictionary archive are never included.

**Incognito windows.** If you enable the extension for incognito windows in Chrome's settings, it runs in Chrome's default spanning mode: there is no separate incognito profile, so anything a save or the reader persists (an offline-queue entry when you save while offline, a reader handoff, reader highlights you create, AI caches) is written to the same on-device storage the regular windows use and remains there after the incognito window closes. Bookmarks saved from an incognito tab default to private on Pinboard, but that flag does not change what is stored locally. If you do not want incognito browsing reflected in on-device extension data, do not enable the extension for incognito windows. There is no single action that clears all of it afterwards: the options page's Storage Management panel only reclaims a handful of `chrome.storage.local` caches (page extraction, bookmark URLs, tags, and AI-usage, compatibility, dictionary-failure and dictionary empty-result memos); reader highlights and notes are managed from the Library page instead; the offline save queue can be emptied from the popup's offline-queue bar (remove one entry or clear all) or drains itself once a queued bookmark is successfully replayed; and the AI result caches (tags, summaries, translations, and dictionary lookups) live in IndexedDB, bounded only by per-cache entry limits, with no manual clear control today. Complete AI dictionary entries and supplements are kept separately as persistent records and are not removed by cache eviction.

Credentials are excluded unless you tick **Include API keys and tokens in backups**, which is off by default. With it ticked, the export writes your Pinboard, Karakeep and linkding tokens, any Karakeep or linkding access gateway credentials, every AI provider key, and the Jina, Wayback, AnkiConnect, Eudic, GitHub and Notion tokens and the Webhook authorization value or capability URL into the file in plain text, marks the file `with credentials` in its name, and records the fact in the file's metadata. Such a file is equivalent to a password file: anyone who opens it can use those credentials. On import, credentials are a separate section that stays unticked even when the file contains them, so restoring settings never silently overwrites the keys already working on that device.

## Chrome Web Store data categories

The Chrome Web Store privacy form uses standardized data categories. To keep the store listing consistent with this policy, this extension discloses that it handles the following categories:

| Category | Why it applies |
|----------|----------------|
| Personally identifiable information | Your Pinboard API token includes your Pinboard username; account-scoped local state and cache keys store that username owner in plaintext locally (without the token), including offline, tag, AI, Batch, tag-cleanup, and reader state. After you connect Google Drive, the connected Google account's email address and display name are also stored locally |
| Authentication information | The extension stores and uses credentials you provide, such as your Pinboard, Karakeep or linkding API token, access gateway headers for Karakeep or linkding, AI/Jina provider keys, Wayback S3 credentials, GitHub token, webhook authorization value or capability URL, AnkiConnect API key, Eudic OpenAPI authorization value, Notion internal integration token, and the Google OAuth token used for Google Drive sync |
| Web history | The extension reads page URLs and titles for bookmark status, popup prefill, Batch Save, Save Tab Set, offline queue, and bookmark/export metadata |
| Website content | The extension can extract page text, selected text, links, metadata, highlights, and notes for AI tags/summaries, the reader, Translate, Ask-the-page, Explain-selection, Dictionary lookups and the vocabulary book, exports, manual backup files, and Google Drive sync |

The extension does **not** collect health information, financial/payment information, location, personal communications as a separate category, or user activity for analytics/tracking. It has no developer-operated analytics, telemetry, advertising, or profiling.

The personal library is shared across bookmark services. Its non-secret identity is retained when you switch services or sign out. On upgrade the current Pinboard username is adopted once to preserve existing local and Drive records; other historical accounts are not merged. A new installation without Pinboard uses a personal-library identity. Settings sync can carry this identity to your other devices. A settings-only JSON import does not switch it. On a fresh, empty library with no Drive connection, explicitly importing vocabulary or highlights can adopt their common backup identity after the preview discloses this. Otherwise data-section imports require a matching library identity. Karakeep/linkding credentials are bound to their verified server URL; a synced address alone cannot redirect a locally stored token. Bookmark caches, drafts, reader bookmark metadata and offline work remain scoped to the original service connection. Karakeep connections include the verified user ID; linkding creates a new opaque connection ID on each explicit reconnection because its API does not expose a stable user ID.

## Network requests

Opening saved Ask history reads local data and never calls an AI provider. Clicking **Continue in reader** can request access to the article’s exact origin, open its page, and extract it again locally; it does not upload the full article to the history archive. Another AI request occurs only when you submit a new question or regenerate an answer.

Pinboard hosts remain required at installation for Pinboard features. A Pinboard account is not required when you select Karakeep or linkding. Every other destination the extension contacts itself (Karakeep, linkding, AI providers, Jina, Wayback, Gist, Webhook, Notion, the online dictionary, Eudic, AnkiConnect, Google Drive, and YouTube and bilibili subtitles), and every site selected for Batch Save, requires an optional grant for that **exact origin**, as each item below describes. Permission prompts are initiated only from a direct user action; automatic and background feature paths only check an existing grant and skip or fail safely when it is absent. Remote images retained in the reader are normal browser subresource requests and do not use an extension host-permission grant; they are disclosed separately below.

Reader exports can include completed Ask-the-page questions and answers, numbered citations, quoted source excerpts, source URLs, and model and generation-time metadata. You can choose a conversation-only export or opt in to appending conversations to the article; appending is off by default. Download and copy actions keep that content in a file or on your clipboard. An explicit Send-to action passes the selected content to the existing destination described below, including any questions, answers, and quoted excerpts you chose to include. Selecting export content does not send it automatically.

1. **Pinboard API** (`api.pinboard.in`): to save, retrieve, and manage your bookmarks, including saves, edits, and confirmed deletions from the reader, authenticated with your Pinboard API token. The **tag-cleanup tool**, when you run it, downloads your full bookmark/tag list (`posts/all`, `tags/get`) and re-saves affected bookmarks to rename or merge tags, all to and from your own Pinboard account. The extension also checks whether the current page is already bookmarked as you navigate, sending the active tab's URL to the Pinboard API to set the toolbar icon state. If you turn on the unread-count badge or the Prewarmed tag cache, the extension also polls your own Pinboard account every 15 minutes for the unread count or the tag list.

2. **Pinboard website** (`pinboard.in`): (a) a content script applies your chosen theme CSS and tag-sort tweaks on pinboard.in pages; no data is extracted or transmitted. (b) **Save Tab Set** POSTs the open tabs' titles and URLs to `pinboard.in/tabs/save/` using your existing pinboard.in **login session cookie** (not the API token), then opens `pinboard.in/tabs/show/` for you to confirm.

3. **AI provider APIs**: the page title, URL, and extracted article text are sent to **the provider you chose** to generate AI tags, summaries, translations, Ask-the-page answers, selection explanations/translations, Batch Save results, AI dictionary entries, or AI punctuation for video subtitle transcripts (clicking the **AI punctuation** button in the reader for a video page sends that video's full transcript text to the provider across multiple batches). On a YouTube or bilibili video page, when the subtitle origin grant already stands and the option **Use video subtitles as the AI content source** is on (the default), the popup's AI tags and summary send the video's subtitle transcript in place of the page text, within the same size window; without that grant they use the page text as before. Tag/summary requests send at most about 4,000 characters of extracted text, taken from the beginning and the end of the article. AI-tag requests can also include up to 50 existing Pinboard tag names so the provider can prefer reuse. If you put `{{description}}` in a custom tag or summary prompt, the current bookmark description or notes are included. Full-text Translate sends the translatable article across multiple batches; it is not reduced to one sampled context window. Translate does not create a summary, but when a summary generated under the current bookmark connection is already cached locally, that summary is included as context in each translation batch. The extension operates no translation snapshot or sharing service: translations stay on your device and with the AI provider you chose, unless you explicitly send them somewhere with a Send-to export action (items 6, 7, 8, 18, and 19). Ask-the-page and the opt-in key-points skim select article context within their token budgets. **Generate AI entry** in the reader or Library page sends the queried word or phrase, its language, and the requested explanation language to your configured AI provider using the reader model setting. The explanation language follows your explicit choice, otherwise your stated native language, otherwise the interface language. Basic entry generation does not retrieve word-origin sources. Word origins and related words are a separate manual supplement using the language-specific Wiktionary origin described in item 22. It sends no article title, source sentence, article text, or imported dictionary definitions. The result contains general meanings and usage; the separate **Explain** action uses article context as described above. Complete AI entries are saved on this device and, after Google Drive is connected, synced for reuse on other devices without another generation request. The initial view can prefer the dictionary, prefer saved AI entries, or prefer AI and generate a missing entry. Only the last choice enables automatic generation, while reader AI is enabled and the provider origin grant is active. New installations default to the dictionary; upgrades preserve the prior automatic-generation choice. The **Usage points** (collocations and sentence patterns, confusing words) and **Word origin** supplements are separate manual actions, one request each. Each sends the saved entry’s meanings and your optional native language from settings to the same configured AI provider; the confusing-words and word-origin requests also send their category and optional learning level; no topic or usage situation is entered or sent. Only the word-origin supplement additionally sends the retrieved Wiktionary passages and source metadata described in item 22; when none are found, it asks only for modern word formation. Search results locate candidates; source text is then fetched and checked before it is used. Original-text examples are only retrieved from Wikisource and displayed (item 22); they are never sent to an AI provider. The generated supplement, its explanation language and structured teaching content, and its source evidence are saved with the entry and follow the same connected Drive sync; generation does not add the word to your vocabulary. Updating an entry or supplement is an explicit action that consumes tokens and retains earlier paid versions. Independently valid supplement items may be saved with a visible incomplete status. Upgrading the extension does not automatically regenerate them. Supplements saved under categories that are no longer offered stay readable, are labelled as an older category, and cannot be updated. Dictionary entries and supplements are received as a stream: while one is being generated, only the current step and the elapsed time are shown, and nothing is displayed or saved until the complete answer has been checked. Generation stops without saving after 180 seconds, when the answer exceeds its output limit, or when you cancel, and is never retried automatically. A generated entry is identified as AI content; it does not replace an original dictionary definition or automatically save a word. A definition you explicitly choose and save becomes ordinary vocabulary data. If you enable AI for Quick Save, Read Later, or Batch Save, the corresponding save action can initiate the configured AI work. If you separately opt in to key-points skim, opening the reader can generate it automatically on a cache miss. **AI deep analysis** in tag cleanup sends tag names (and, when truncated, the number of omitted lower-frequency tags), not bookmark page content or per-tag use counts. Supported providers: OpenAI, Anthropic, Google Gemini, DeepSeek, Alibaba Cloud Model Studio (the region you select, or your workspace's dedicated address in that region), MiniMax, OpenRouter, Groq, Mistral, Cohere, SiliconFlow, Zhipu, Moonshot (Kimi), Volcengine Ark (or BytePlus ModelArk, by the region you pick), OpenCode Zen, Command Code, a **local Ollama** instance, or one or more **custom endpoints** (OpenAI-compatible or Anthropic-compatible). The first direct use requests only that provider's exact origin; later automatic use proceeds only while that exact grant remains active. Each custom endpoint needs its own exact-origin grant from a direct user action, and each one's key is stored only on this device by default. The **Test Connection** button next to each provider sends only a fixed one-line prompt ("Reply with just the word: OK") to that provider, never page content or account data; when a Reader model override is set for the selected provider, the button sends that same prompt a second time using the override model.

4. **Jina Reader** (`r.jina.ai`, optional): when you choose the Jina content source, the page URL is sent to Jina to fetch a cleaner reader-mode rendering for AI processing, the reader, or Markdown export. If you configured a Jina API key, it is sent on a cache miss or refresh as a Bearer authorization value. Disabled by default. A cache hit stays local; a network cache miss requires an exact `https://r.jina.ai` grant.

5. **Wayback Machine** (`web.archive.org`, optional, opt-in): when you enable Wayback archiving, the URL of a page you save can be submitted automatically to the Internet Archive to create a public snapshot. If you configured Wayback S3 access credentials, the access key and secret are sent in the request's authorization header. It is off by default and requires an exact `https://web.archive.org` grant. Background saves only check that grant; if it is absent, the archive is not submitted and the permission-required outcome is logged locally.

6. **Obsidian** (local app, optional): the **Send to Obsidian** action hands the converted Markdown of the current page to your local Obsidian desktop app via the `obsidian://` protocol or the system clipboard. This stays on your device; nothing is sent over the network.

7. **GitHub Gist** (`api.github.com`, optional; inactive until you configure it): the **Send to Gist** action uploads the selected export’s converted Markdown (including its metadata frontmatter and, for article exports while the **Include highlights** export option is on, your highlights and notes for the page) as a **secret gist** on your own GitHub account, authenticated with a personal access token you provide. A secret gist is unlisted, not private: anyone who has its link can open it. The action requests only the exact `https://api.github.com` origin.

8. **Webhook** (a URL you configure, optional; inactive until you configure it): the **Send to Webhook** action POSTs a JSON payload to the endpoint you entered (e.g. Readwise), with an Authorization header value you provide. The payload contains the page's title, URL, a date, tags, and converted Markdown (with your highlights and notes for the page while **Include highlights** is on, the default); when **Include extended metadata** is on (the default), it also includes the clip date, the page's author, original publish date, site name, cover-image URL, and word count. The action requests only that endpoint's exact origin. An unsafe endpoint is blocked rather than warned-and-sent.

9. **Selected Batch Save sites** (local extraction access, not a data destination): when AI is enabled for Batch Save, Chrome asks for the exact origins of the selected HTTP/S tabs so the extension can extract their page text locally, together with the exact current AI-provider origin. The confirmation view lists every requested origin. The extension does not request the all-sites wildcard at runtime; extracted content is sent only to the selected AI provider as described above.

10. **Remote image hosts in the reader**: sanitized Markdown can retain remote image URLs. When the reader renders those images, the browser requests them directly from the original site or image/CDN host without a separate extension host-permission prompt. Every retained image is forced to `referrerpolicy="no-referrer"`, so the referring article or reader URL is not sent in the `Referer` header. The image host still receives the requested image URL and ordinary connection/request metadata such as the user's IP address and browser headers; cookies are included only when permitted by Chrome's cookie and third-party-cookie policies.

11. **Embed (offline) image export in the reader** (image hosts referenced by the exported document, optional): this is a separate mechanism from the ordinary `<img>` rendering described above. Choosing the **Embed (offline)** image policy for a Markdown/HTML/EPUB download makes the extension page itself fetch each remote image directly from its own host (`credentials: "omit"`) and convert it to a data URI (or, for EPUB, bundle it as a file inside the book) so the downloaded file renders offline. This only runs when you click Download with that policy selected, and requires a one-time optional host-permission grant for the exact image origins found in the document; declining leaves those images as ordinary remote links in the export instead of embedding them. Images that fail this plain fetch (typically hosts that reject requests without a `Referer` header) are retried once behind the temporary Referer rule described in item 12, within the same download-size budget. No image data passes through any intermediary.

12. **Fix images blocked by hotlink protection in the reader** (image hosts, optional): some sites reject any image request that carries no `Referer` header, and an extension page can only send referrerless requests, so those images fail to load in the reader. When that happens, the reader shows a count and a **Try to fix this page's images** button. Clicking it asks for a one-time optional host-permission grant for the exact failed image origins, then re-fetches only those images (`credentials: "omit"`) while a temporary declarativeNetRequest **session** rule (scoped to those image domains, to the `fetch` request type, and to that one reader tab) sets the `Referer` header to the article page's **origin** (never the full article URL or its query). The rule is removed as soon as the fetch run finishes, and fixed images are displayed as inline data URIs for that page view only; nothing is written to storage. For image origins you have already granted, later reader pages re-apply this fix automatically; the automatic path only checks the existing grant (`permissions.contains`) and never prompts. Declining the permission leaves the images as broken placeholders. Some image links carry a time-limited signature from their CDN (an expiry or signature parameter in the URL), and no `Referer` revives one that has expired. When the fix gives up on such an image, the reader says the link has expired and offers **Refresh the original page and reload**. Clicking it asks for a one-time optional host-permission grant for the exact origin of the article page (Chrome withdraws the temporary access it granted when you opened the reader as soon as that tab reloads, so extracting the page again needs this grant), then reloads the original tab you opened the reader from (only while it still shows that same page; a tab that has moved on is never reloaded), extracts the article from it again with the bundled extractor, and reloads the reader onto that fresh copy. Nothing is sent anywhere new: the reload is the page's ordinary traffic in your own tab, and declining the permission leaves the reader as it was.

13. **Free Dictionary API** (`freedictionaryapi.com`, optional): when you use the Dictionary lookup in the reader and grant an exact `https://freedictionaryapi.com` origin, the selected word and its language code are sent to fetch Wiktionary-based definitions. The same lookup can also be started from the Library page: clicking the dictionary lookup button on a saved word (including Look up again), submitting the page's own lookup box (an empty box looks up the open word), clicking Look up base form for an unsaved related form, or changing the dictionary language after a lookup has run. After you have granted access to the online dictionary, opening a saved word on that page also looks it up automatically when no installed offline dictionary has an entry for it. Each of these sends that word and its language code to the same endpoint; a result already cached on your device is reused without a request. Opening the page itself sends nothing, and the lookup never runs in the background.

14. **AnkiConnect** (`http://127.0.0.1:<port>`, local loopback, port configurable in settings with 8765 as the default, optional; inactive until you click Send all to Anki or Test AnkiConnect): the **Send all to Anki** action sends every vocabulary book entry in the personal library to a locally running Anki instance through the AnkiConnect add-on. The original format includes term, reading, definition, context quotes, the first article source, license text, and language/group tags. If you choose the separate multilingual format, it also includes language, base form, your note, every context with its own source and metadata, groups, learning status, creation/update times, separate dictionary provenance and any locally derived supplemental definition. A stable WordID is computed on your device by hashing the account-scoped vocabulary identity; the identifier does not embed the plaintext Pinboard username. The multilingual format creates a separate note type and adds new notes while skipping duplicates; it does not migrate or update existing notes. It uses an API key you provide if AnkiConnect requires one. The request always targets the loopback address 127.0.0.1 (only the port is configurable); it never reaches the public internet or the developer. The action is offered in settings and in the Export menu of the Library page; it requests only that exact origin and runs only when you click Send all to Anki. The **Test AnkiConnect** button in settings performs the same handshake against the same loopback origin (plus a version call carrying your API key when AnkiConnect requires one) and sends no vocabulary data.

15. **Eudic OpenAPI** (`api.frdic.com`, optional; inactive until you click Send all supported words to Eudic or Test Eudic connection): the **Send all supported words to Eudic** action checks every vocabulary book entry in the personal library. It sends the term text and language code of entries in a supported language (English, French, German, or Spanish) to your Eudic account's default study list for that language, authenticated with an OpenAPI authorization value you provide. Entries in unsupported languages are skipped and not sent. The action is offered in settings and in the Export menu of the Library page; it requests only that exact origin and runs only when you click Send all supported words to Eudic. The **Test Eudic connection** button in settings sends a single read-only study-list category request to the same origin, carrying only your authorization value and no vocabulary data.

16. **Google Drive API** (`www.googleapis.com`, optional): clicking **Connect Google Drive** is the only action that can request the optional Chrome identity permission and exact `https://www.googleapis.com` origin. The extension uses the `drive.appdata` scope to store immutable batches of the personal library’s vocabulary, highlights, notes, AI dictionary archive, and saved Ask conversations in its private `appDataFolder`, not in your visible Drive files. Vocabulary batches contain plaintext words, languages, base forms, definitions, IPA, groups, notes, source URLs, article titles, context excerpts, source-license data, and timestamps. This includes definitions you explicitly save from dictionary results on the Library page, including your imported offline dictionaries. A lookup saved without an article does not invent a context sentence or article source. Highlights-and-notes batches contain the personal library’s highlighted excerpts, notes, source URLs and titles, colors, timestamps, and anchor information; Drive sync does not upload or claim unowned legacy records. AI dictionary batches contain complete entries and requested supplements, including their learner profile (with the topic that older supplements were requested for), cited source excerpts/URLs/titles, provider/model and generation time. They are synced even when the word has not been saved to the vocabulary book. AI dictionary batches now use a newer format that adds collocations-and-sentence-patterns supplements, and an updated device writes every new AI dictionary batch in it. A device still running an earlier version of the extension does not receive those new records until it is updated; records synced before are unaffected. Ask batches contain article URLs/titles, completed questions and answers, citation excerpts and verification status, model and time, session IDs, earlier answer versions, and deletion markers; they do not contain the full article or temporary conversations. Vocabulary batches also preserve causal versions of concurrent edits so devices can merge them consistently. All batch types contain an owner hash, a device identifier, and record keys. Vocabulary and note batches also contain version vectors, dots, and deletion markers used for convergence; the plaintext library identity and all credentials are excluded. The extension calls Drive `about.get` to identify the connected account and stores its permission ID, email address, and display name locally with cursors, pending work, errors, and retry state. After a device is connected, pending local changes can schedule a sync after 30 seconds and a periodic check can run every 15 minutes. These automatic runs only check existing permissions and never open an OAuth prompt. **Disconnect this device** removes the cached OAuth token and optional grants but does not delete local vocabulary, highlights, notes, AI dictionary records or saved Ask conversations, local convergence state, or remote `appDataFolder` batches.

17. **Browser speech synthesis for pronunciation** (no extension permission involved): the pronunciation button in the Dictionary lookup uses the browser's built-in Web Speech API. The extension prefers a voice the browser reports as running on your device, so in the common case the word never leaves your computer. Some voices are network-backed instead; on desktop Chrome these are the built-in "Google *language*" voices, which synthesize speech on Google's servers. If your browser offers no on-device voice for the detected language, or no language was detected, the browser can fall back to one of those network voices, and the text being spoken (the selected word or phrase, truncated to 200 characters, never the article) is sent to that speech service by Chrome itself. This path uses no extension host permission, so there is no permission prompt to accept or decline; which voices exist and which is used by default are controlled by your operating system and your Chrome settings.

18. **Notion** (`api.notion.com`, optional; inactive until you configure it): the **Send to Notion** action creates a new page under a parent page you choose in your own Notion workspace, authenticated with an internal integration token you provide. The request carries the page's title, source URL, tags, and the selected export’s converted Markdown as the new page's content, including your highlights and notes for the page while **Include highlights** is on (the default). The action requests only the exact `https://api.notion.com` origin.

19. **NotebookLM** (no network access; optional): the **Send to NotebookLM** action copies the converted Markdown to your system clipboard and opens `notebooklm.google.com` in a new tab. The extension itself sends nothing over the network and requests no host permission for it; the content reaches Google only if you paste it there yourself.

20. **YouTube video and subtitles in the reader** (`www.youtube.com`, optional; only when the reader opens a YouTube video page): opening a YouTube video page in the reader automatically requests a poster thumbnail from `https://i.ytimg.com/vi/<id>/hqdefault.jpg` for the entry card; this is an ordinary `<img>` request with `referrerpolicy="no-referrer"` set, and, as with other retained reader images (item 10), cookies are included only when Chrome's cookie and third-party-cookie policies would otherwise send them to that host. The first time you use this on a video page, an **Enable subtitles & load video** button asks once for the exact `https://www.youtube.com` origin; no watch-page, subtitle, or player request is made before that click (the poster thumbnail described above is the only request that precedes it). Once that grant stands, opening a YouTube video page in the reader runs the subtitle capture automatically (the extension only checks the existing grant, it never re-prompts), because the transcript now IS the page's article rather than an optional panel. With that grant, if a `www.youtube.com` tab is open in your browser (preferring the tab this reader page came from), the video's ordinary watch page and the selected subtitle track are read inside that tab, with the tab's own session: the same requests that page could make itself, sending nothing beyond what your own YouTube session already sends. When that direct route is withheld, the extension may instead drive that tab's own player to load the subtitles, or open and read YouTube's own transcript panel in that tab; both act only within that tab and send nothing beyond what the page itself would. When no YouTube tab is open, the extension falls back to requesting the same watch page and track text directly from the reader page; only this fallback is governed by **Send YouTube login cookies with subtitle requests** (on by default, because an anonymous fallback request is more likely to be treated as automated traffic and refused outright; turning it off makes the fallback cookieless, `credentials: "omit"`, at the cost of finding subtitles less often). YouTube restricts subtitle access for some videos, and those simply report no subtitles. Clicking the entry card also loads the player, embedded through a small page published on this project's own GitHub Pages site (`pine2d.github.io`), which exists only because Chrome sends no `Referer` from extension frames and YouTube's player refuses to load without one; that relay page builds the player through YouTube's own IFrame API, loading YouTube's official player script (`iframe_api`, which loads `www-widgetapi.js` in turn) only on the Pages origin and never inside the extension. It forwards play and seek commands from the reader, reads back the player's public playback position and state through that same official API, and reports them only to the reader page that first messaged it, an origin captured from and checked against that first message; it stores nothing. It uses the ordinary YouTube domain rather than the privacy-enhanced `youtube-nocookie.com` one because the latter is a separate domain that your login cookies never reach, which made YouTube treat the embedded player as automated traffic and refuse to play. The tradeoff is the cookies the ordinary domain sets, the same ones any YouTube embed on any website sets. Loading the relay needs no host-permission grant, since it is a frame rather than a fetch, so the player still loads even if you decline the subtitle-origin prompt. An always-present **Open on YouTube** link next to the player opens the ordinary `youtube.com/watch` page in a new tab, as a fallback for when the relay cannot load. With the grant standing, opening such a page in the reader also loads the embedded player automatically. Nothing is sent for non-YouTube pages, and revoking the origin in Chrome's site settings returns the page to the ask-first state. The popup's AI tags and summary reuse this same standing grant to read the subtitles as their content (see item 3): they only ever check that the grant exists and never prompt for it.

21. **Bilibili subtitles in the reader** (`api.bilibili.com`, optional; only when the reader opens a bilibili video page): the first **Enable subtitles & load video** click asks once for the exact `https://api.bilibili.com` origin; once that grant stands, opening a bilibili video page in the reader automatically calls bilibili's view, nav, and WBI-signed player endpoints to list and fetch subtitle tracks. Because bilibili only returns subtitles to a logged-in account, these three requests are sent with your bilibili **login cookies** (`credentials: "include"`, first-party to bilibili's own API, the same session your browser already holds); the subtitle text file itself is fetched from bilibili's CDN without cookies. Signed in, this reads your session's subtitle access; signed out, bilibili returns an empty list and the panel shows a sign-in hint. The embedded player loads from `player.bilibili.com` inside a frame, automatically once the grant stands (the transcript is the page's article). The same click also asks for the exact `https://player.bilibili.com` origin: with it, the extension registers a small script that runs only inside `player.bilibili.com` frames and stays inert until a reader page of this extension greets it; it then reports the player's current time, play/pause state and duration to that reader page and nowhere else (every message is addressed to this extension's own origin) and accepts seek / play / pause / speed commands from it, so the transcript can follow playback the way it does for YouTube. It reads nothing else from the player page and sends nothing to bilibili. Nothing is sent for non-bilibili pages, and revoking either origin returns the page to the ask-first state (without the player origin, the transcript falls back to jump-on-click only). The popup's AI tags and summary reuse this same standing grant to read the subtitles as their content (see item 3): they only ever check that the grant exists and never prompt for it.

22. **Wikimedia dictionary and usage sources** (language-specific Wiktionary and Wikisource origins, optional): The separate word-origin supplement retrieves public evidence from the word’s language edition of Wiktionary only when explicitly requested or updated. That action may request the exact origin. Basic entry generation does not contact Wikimedia. Clicking **Find examples in texts** searches the language’s Wikisource edition for original sentences that contain the word; it works whether or not AI is enabled or configured. That click requests only the exact Wikisource origin, never an AI-provider origin. Each example shows one retrieved sentence or verse line with its author, work, location and a revision link, without translation. Examples are never sent to an AI provider and are not saved, cached or synced; finding them again repeats the search. Only an empty search is remembered on this device, as a hashed marker described in the local data table, so the next lookup can offer a retry. Cultural or internet usage supplements are no longer generated or retrieved; ones saved earlier remain readable with their saved source links, which open only when you click them. Requests send the word or phrase, then candidate page or section identifiers needed to read the original text and its metadata, without article context or imported dictionary data. For word origin, the action requests only the Wiktionary origin and the configured AI origin, when needed; short source passages with titles, links and relevant author/work/location/language/genre/revision metadata are used for the AI explanation, and the evidence and retrieval time are also saved and synced. Search snippets alone are not treated as verified quotations. Source availability and recognized structures vary by language; these searches do not guarantee coverage of modern copyrighted literature or current slang. Other supplement categories do not query Wikimedia.

For configured AI and Webhook destinations, HTTPS is required. Plain HTTP is accepted only for the literal loopback hosts `localhost`, `127.0.0.1`, and `[::1]` (with an optional port). Public or LAN HTTP hosts, alternate loopback spellings, wildcard hosts, and URLs containing embedded credentials are blocked before any request. The configuration is retained so you can correct it; permission denial or revocation likewise preserves keys and settings.

Page content, URLs, credentials, and remote-image requests are transmitted only as described above, and never to the developer.

23. **Karakeep / linkding APIs** (your configured server, optional): **Connect** requests access to that exact origin and checks your API token with a read-only profile request. The selected service receives bookmark URLs, titles, notes, tags and read-later/sharing choices for popup, reader, shortcut and batch saves, updates and deletions. linkding also receives a single-line description, kept separate from notes. Enabled bookmark-status checks send the current page URL; tag completion and recent-bookmark panels retrieve your own records; offline retries send pending saves for the same connection. Karakeep uses a dedicated private manual list owned only by you for Read Later, creates it when needed and adds or removes bookmark membership. It does not change Karakeep’s archive flag. If another client saves the same URL after the extension checks for it, Karakeep itself merges the create request into that bookmark, removes it from the archive and updates its save time. linkding uses its unread flag. Every linkding bookmark check the extension makes (the enabled status checks, the popup and reader lookups, and the check before each save) also has your linkding server load the checked page itself to read its title and description; linkding may reuse a copy it loaded recently. When the extension creates a linkding bookmark and has a description it can vouch for, it sends that description and sets `disable_scraping` to ask the server not to scrape the page title or description itself. That description is an AI summary, the page’s meta description, your own text or the description of a bookmark loaded into the form, which stays with the form when you change its address. It is empty when you clear it, when the page has no meta description or one that only repeats its title, when automatic page descriptions are turned off, or when the loaded bookmark has none. Otherwise the extension sends no description and does not set `disable_scraping`, so linkding fetches the page to fill in the description itself, as it does by default. That happens when there is no AI summary, text of your own or description of a loaded bookmark, automatic page descriptions are on, and the extension could not read the page, the address in the form is not the page the popup was opened on, or a save from the reader received no description from the popup. New linkding bookmarks are unshared by default; they are shared only when you select Share. Requests use the API token in an authorization header, omit browser cookies and reject redirects. If you configure an access gateway, such as a Cloudflare Access service token, requests also carry the gateway headers you provide, sent only to the exact origin of that server and never to a redirect target. These services do not receive your vocabulary, highlights, notes from the reading library, AI dictionary archives or Ask history through this integration. An API without conditional writes cannot guarantee conflict prevention against simultaneous edits by another client.

- **Eudic OpenAPI** ([API docs](https://my.eudic.net/OpenAPI/Doc_Index)): your Eudic account's default study lists receive the term text and language code of every supported-language vocabulary book entry in the personal library only through an explicit Send all supported words to Eudic action, authenticated with an OpenAPI authorization value you provide (the Test Eudic connection button sends a single read-only category request and no words); unsupported languages are skipped
- **Your browser's speech-synthesis service**: when you use the pronunciation button, the extension asks the browser to speak the selected word or phrase. It prefers an on-device voice. If the browser resolves the request to a network-backed voice instead (on desktop Chrome, the built-in "Google *language*" voices), Chrome sends that text to its speech service; the extension holds no host permission for this path and cannot intercept it
- **Offline English–Chinese dictionary pack (ECDICT CSV field layout)**: a dataset you obtain and import yourself. The extension reads that field layout; it does not provide, recommend or verify a source for the data, links to none, and is not affiliated with any. Importing the pack and looking up a word that matches it happen entirely on your device and add no network endpoint. When a lookup matches, the Chinese definitions appear above the English entry, which still loads exactly as before. Vocabulary exports (the TSV download and Send all to Anki) can include the matching Chinese text derived on this device, labelled as coming from your local pack; a device without the pack produces the same export without those pieces. Export-only enrichment is not written back into your vocabulary book or sent to Google Drive. Separately, if you explicitly choose a local definition and save it from the Library dictionary results, that definition becomes saved vocabulary and follows your existing backup, export and connected Google Drive settings. Importing a pack or merely displaying a result does not save its definitions to the vocabulary book.
- **CC-CEDICT** ([cc-cedict.org](https://cc-cedict.org/wiki/)): an open Chinese-English dictionary dataset licensed CC BY-SA 4.0 that you download from MDBG and import yourself; the **Open download page** button only opens that page in a new tab; importing the pack and looking up a word that matches it happen entirely on your device and add no network endpoint; a lookup that misses the pack still falls back to the Free Dictionary API described above, while AI entry generation independently uses your selected provider under the controls described above
- **Multilingual offline dictionaries (Yomitan v3 ZIP)**: files you obtain and import yourself. The extension imports words, readings and text definitions into local storage; it does not import styles, images or audio. Source languages, definition languages, source URLs and license statements come from the file or details you supply; the extension does not verify the rights to the data. The links to the Yomitan dictionary directory, Wiktionary-to-Yomitan and Jitendex open their official pages in a new browser tab so you can obtain files yourself; they do not fetch or install a dictionary automatically. Each installed dictionary has a local enabled setting. AI entry generation does not send imported dictionary content to the AI provider. Imports and local lookups add no network endpoint. A replacement becomes active only after a successful import. Packs stay on this device and are excluded from Drive sync and manual JSON backups. Merely displaying a result does not add it to the vocabulary book; a definition you explicitly choose and save becomes vocabulary data and follows the existing backup, export and connected Drive behavior described above.

Optional-service permission denial or revocation sends nothing to that destination and does not erase its configuration. Selected Batch sites are accessed only to extract the content requested for that batch; they do not receive data from the extension.

Other than the services, configured destinations, Chrome Sync, and remote image hosts described above, the extension does not intentionally send data to third parties. No data is sent to the developer.
